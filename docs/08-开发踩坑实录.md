# 开发踩坑实录：客户详情页

> 这一节记录了在给项目新增"客户详情页"（`app/dashboard/customers/[id]/page.tsx`）过程中遇到的所有坑。
> 每个坑都包含：现象、根本原因、修复方法、教训。
> 这些坑在以后开发类似功能（列表页、详情页、表单）时会反复出现，值得反复对照。

---

### 坑 1：`'use client'` 和 `async` 同时出现在一个组件上

**报错信息**：
```
<CustomersTable> is an async Client Component. Only Server Components can be async.
```

**根本原因**：为了让客户头像/名字可点击跳转，给 `app/ui/customers/table.tsx` 加了 `'use client'`，但这个组件本身又是 `async function`。在 Next.js 里这两者互斥：
- 服务端组件**可以** async（在服务器上 await 查数据库）
- 客户端组件**不能** async（浏览器没法 await 查数据库）

**错误的修复思路**：用 `onClick` + `useRouter().push()` 实现跳转 → 会让整个组件变成客户端组件，丢失服务端组件的好处，而且 `<p onClick>` 语义不对、失去右键新标签页等浏览器原生能力。

**正确修复**：跳转用 `<Link>` 组件。`<Link>` 渲染成 `<a href>`，浏览器原生导航，**不需要任何 JavaScript 事件监听**，能在服务端组件里直接用。去掉 `'use client'`，把交互需求用 Link 解决。

```tsx
// ✅ 服务端组件里用 Link 跳转，不需要 'use client'
<Link href={`/dashboard/customers/${customer.id}`}>
  <Image ... />
  <p>{customer.name}</p>
</Link>
```

**教训**：凡是"跳转到另一个 URL"的需求，优先用 `<Link>`，不要用 `onClick + router.push`。只有"跳转前要先跑复杂逻辑"才考虑后者。

**涉及知识点**：Server/Client Component 边界、`<Link>` vs `onClick`、浏览器原生表单/导航能力

### 坑 2：查询函数照抄了列表页的复杂逻辑（过度设计）

**现象**：`fetchCustomerById` 一开始写了 LEFT JOIN + GROUP BY + COUNT + SUM 一大堆，和 `fetchFilteredCustomers` 一模一样。

**根本原因**：从客户列表页的查询函数复制过来的。但**列表页需要"每个客户的统计"**（所以要 GROUP BY），而**详情页只需要"一个客户的信息"**——统计可以用 JS 算（发票列表已经在手）。

**修复**：简化成最朴素的 SELECT：

```ts
// 修复前：LEFT JOIN + GROUP BY + COUNT + SUM（抄列表页的）
// 修复后：
export async function fetchCustomerById(id: string) {
  const data = await sql<Customer[]>`
    SELECT id, name, email, image_url
    FROM customers
    WHERE id = ${id}
  `;
  return data[0];
}
```

统计移到页面用 JS 算：

```ts
const total_invoices = invoices.length;
const total_pending = invoices
  .filter((i) => i.status === 'pending')
  .reduce((sum, i) => sum + i.amount, 0);
```

**教训**：别盲目复制兄弟文件的代码。复制前先问"这个页面到底需要什么"，匹配当前需求，而不是照搬结构。判断标准：对着 SELECT 的每个字段问"页面用到了吗"，没用到就删。

**涉及知识点**：SQL GROUP BY、聚合函数、查询按需设计

### 坑 3：金额单位（分/元）转换混乱

**现象**：详情页的"待处理""已收款"统计显示成一长串数字 `15795`，而不是 `$157.95`。

**根本原因**：数据库 `amount` 列存的是**整数分**（`15795` = $157.95）。项目里有个 `formatCurrency` 函数专门做"分→元"的转换（内部 `/100` 再加 `$` 符号）。把统计从 SQL `SUM` 移到 JS `.reduce` 后，求和结果还是"分"，但页面**直接显示了数字**，漏了 `formatCurrency` 这一步。

**修复**：任何金额显示都要套 `formatCurrency()`：

```tsx
// ❌ 直接显示数字（显示成 15795）
{total_pending}

// ✅ 套上 formatCurrency（显示成 $157.95）
{formatCurrency(total_pending)}
```

**金额处理的完整链路**（牢记）：
```
数据库 amount（INT，存分）  例：15795
        ↓ 查询函数返回原始"分"
页面拿到 number 类型的分    例：15795
        ↓ 用 formatCurrency() 格式化
显示给用户                  例：$157.95
```

**教训**：金额在数据库里**永远是整数分**，显示时**必须**用 `formatCurrency` 转"元"。从 SQL 移到 JS 算统计时，最容易漏掉这一步。

**涉及知识点**：金额单位约定（分为何不用元）、formatCurrency、浮点数精度问题

### 坑 4：多余的 `{ ...data[0] }` 展开（无意义浅拷贝）

**现象**：
```ts
const customer = {
  ...data[0],
};
return customer;
```

**根本原因**：无意义的浅拷贝。`{ ...data[0] }` 只是把 `data[0]` 复制了一份新对象，没做任何加工，等于白写。

**修复**：直接返回：

```ts
return data[0];
```

**教训**：每一行代码都要问"必要吗"。展开运算符 `...` 只有在"要修改某些字段"或"合并多个对象"时才需要，纯传递数据时是多余的。

**涉及知识点**：展开运算符、对象引用

### 坑 5：`Promise.all` 类型推导失败（混合返回类型）

**报错信息**：
```
Parameter 'i' implicitly has an 'any' type.
Parameter 'invoice' implicitly has an 'any' type.
```

**根本原因**：两个查询函数返回类型不同（`Customer | undefined` 和 `InvoicesTable[]`），`Promise.all` 解构出来的变量类型推导不出来，导致后面 `.filter` / `.map` 的参数全成了 `any`。

**错误的修复**：用 `Promise.all<[A, B]>(...)` 显式泛型 → 和 `postgres` 库的 `RowList` 类型打架，报更复杂的错。

**正确修复**：解构到单独变量，各自加类型注解：

```ts
const [customerData, invoicesData] = await Promise.all([
  fetchCustomerById(id),
  fetchInvoicesByCustomer(id),
]);
const customer: Customer | undefined = customerData;
const invoices: InvoicesTable[] = invoicesData;
```

**教训**：`Promise.all` 混合多种返回类型时，别硬塞泛型，分开标注更干净。TS 的泛型推导对"不同类型的元组"不擅长，显式注解最省事。

**涉及知识点**：TypeScript 泛型推导、Promise.all、postgres 库的 RowList 类型

### 坑 6：JOIN 查了一堆页面没用到的字段

**现象**：`fetchInvoicesByCustomer` 用 JOIN 把 `customers.name, email, image_url` 都查出来了，但详情页的发票表格只显示**金额、日期、状态**三个字段，客户信息已经由 `fetchCustomerById` 单独查过了。

**修复**：删掉 JOIN 和没用到的客户字段：

```ts
// 修复前：JOIN customers，查 7 个字段（其中 3 个没用）
// 修复后：只查发票本身的 4 个字段
const invoices = await sql<InvoicesTable[]>`
  SELECT id, amount, date, status
  FROM invoices
  WHERE customer_id = ${customerId}
  ORDER BY date DESC
`;
```

**教训**：对着 SELECT 的每个字段问一句"页面用到了吗"。JOIN 的成本不低（数据库要做匹配运算），能不 JOIN 就不 JOIN。客户信息已经查过一次，没必要在发票查询里再 JOIN 一次。

**涉及知识点**：SQL JOIN 的成本、查询字段按需选取

### 坑 7：`<form action>` 不允许返回值（deleteCustomer 类型不匹配）

**报错信息**：
```
Type '() => Promise<{ message: string; }>' is not assignable to type
'(formData: FormData) => void | Promise<void>'
```

**根本原因**：`<form action={fn}>` 绑定的函数必须返回 `void`（无返回值）。但 `deleteCustomer` 的"拒绝删除"分支 `return { message: '...' }`，类型不兼容。

**对比**：
- `createCustomer` / `updateCustomer` 用 `useActionState` 调用 → 能 `return`（state 接住错误信息显示在表单旁）
- `deleteCustomer` 用 `<form action>` 直接绑定 → 不能 `return`，只能 `throw`（由 error.tsx 兜底）

**修复**：把 return 改成 throw：
```ts
// ❌ return（form action 不接受）
if (invoiceCount > 0) {
  return { message: '该客户还有发票...' };
}

// ✅ throw（被 error.tsx 捕获显示错误页）
if (invoiceCount > 0) {
  throw new Error('该客户还有发票，请先删除或转移发票。');
}
```

**判断标准**：看 Server Action 怎么被调用的——用 `useActionState` 的能 return，用 `<form action>` 直接绑定的只能 throw。

**涉及知识点**：Server Action、form action 的类型约束、throw vs return

### 坑 8：`redirect()` 放在组件渲染过程里导致页面消失

**现象**：在详情页加了删除按钮，结果详情页"不显示"——页面一打开就跳走了。

**根本原因**：把 `redirect()` 写在了组件函数体里，组件还没渲染出来就执行跳转了：
```tsx
// ❌ 错误：组件渲染时就 redirect 了，return 永远到不了
export function DeleteDetailCustomer({ id }) {
  redirect('/dashboard/customers');  // ← 组件一渲染就跳走
  return <form>...</form>;           // ← 永远到不了
}
```

**修复**：`redirect` 只能放在 Server Action 里（删完数据之后跳），不能放在组件渲染过程里。详情页用带 redirect 的单独 action：
```ts
// customer-action.ts
export async function deleteCustomerAndRedirect(id: string) {
  await prisma.customer.delete({ where: { id } });
  revalidatePath('/dashboard/customers');
  redirect('/dashboard/customers');  // ← 在 action 里，删完后才跳
}
```

**教训**：`redirect` 是 Server Action 专用，在组件渲染过程里调用会导致页面直接跳走、内容不显示。

**涉及知识点**：redirect 的正确使用位置、组件渲染时机

### 坑 9：CSV 导出的状态值大小写不一致（隐藏 bug）

**现象**：CSV 导出后，状态列显示的还是英文 `paid`/`pending`，不是中文"已支付"/"待处理"。

**根本原因**：`formatStatus` 判断的是大写 `'SAID'`/`'PENDING'`，但数据库里存的是小写 `'paid'`/`'pending'`。所有状态都走到 `default` 分支，返回原始英文值。

```ts
// ❌ 大写（和数据库不匹配）
case 'PAID': return '已支付';      // 数据库里是 'paid'，永远匹配不到
case 'PENDING': return '待处理';

// ✅ 小写（和数据库一致）
case 'paid': return '已支付';
case 'pending': return '待处理';
```

**教训**：处理枚举值（status、type 等）时，**判断的大小写必须和数据库存的完全一致**。先去数据库或 Prisma schema 确认存的是什么值，再写判断。

**涉及知识点**：枚举值一致性、switch case

### 坑 10：CSV 导出 API 的类型推导失败

**报错信息**：
```
Parameter 'invoice' implicitly has an 'any' type.
```

**根本原因**：`prisma.invoice.findMany({ include: { customer: true } })` 返回的类型在某些场景下推导不出来，导致 `.map((invoice) => ...)` 的 `invoice` 变成 `any`。

**修复**：给 `invoices` 显式标注类型：
```ts
import type { Invoice } from '@prisma/client';

type InvoiceWithCustomer = Invoice & { customer: { name: string; email: string; image_url: string } };

const invoices: InvoiceWithCustomer[] = await prisma.invoice.findMany({
  include: { customer: true },
});
```

**教训**：Prisma 查询结果在某些上下文（API 路由、复杂 include）里类型推导不稳定，显式标注最稳妥。

**涉及知识点**：Prisma 类型推导、显式类型注解

### 坑总结速查表

| 坑 | 关键词 | 一句话修复 |
|----|--------|-----------|
| 'use client' + async | async Client Component | 跳转用 `<Link>`，别用 onClick |
| 查询过度设计 | 照抄列表页 | 统计用 JS 算，SQL 只查基本信息 |
| 金额显示成数字 | 分/元转换 | 显示必套 `formatCurrency` |
| 多余的对象展开 | `{ ...data[0] }` | 直接 `return data[0]` |
| Promise.all 类型失败 | implicitly any | 解构到单独变量，各自加注解 |
| JOIN 多余字段 | 查了没用 | 对照页面删没用的字段 |
| form action 返回值 | not assignable to void | delete 用 throw 不用 return |
| redirect 放组件里 | 页面不显示 | redirect 只放 Server Action 里 |
| 枚举值大小写 | 状态没转成中文 | 判断的大小写要和数据库一致 |
| CSV 类型推导失败 | implicitly any | 给查询结果显式标注类型 |

### 三条通用原则（从这 6 个坑提炼）

这 6 个坑背后是 3 个反复出现的主题，记住它们能少踩大部分坑：

#### 原则 1：按需写代码
每一行都问"这个页面/组件真的需要吗"，没用到就删。
适用：查询字段、import、组件属性、SQL JOIN。

#### 原则 2：理解单位约定
数据库存什么单位（分/ISO 日期/UUID），显示前怎么转换，要心里有数。
适用：金额、日期、ID。

#### 原则 3：服务端 vs 客户端
展示=服务端组件，交互=客户端组件，跳转优先用 Link。
适用：所有组件设计决策。
